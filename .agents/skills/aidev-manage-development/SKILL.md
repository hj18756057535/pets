# 开发协作主流程

先读当前用户目标、已有主档、项目规则和真实代码状态。遵循 [复用与简化约束](../aidev-keep-changes-simple/SKILL.md)，只加载当前需要的领域 Skill。

负责选择工作路径、维护计划与上下文、衔接领域能力和记录协作日志；业务规则、界面行为、API、Schema 与代码细节由对应 Skill 维护。项目从零开始后，日常迭代继续使用同一入口，不重新初始化或重复走产品发现。

## 按任务选能力

| 当前问题 | 使用的能力 |
|---|---|
| 用户、范围、规则或验收条件不清 | `aidev-define-product-requirements` |
| 页面流程、交互状态或操作反馈要设计 | `aidev-design-interaction` |
| 界面、后端或本地数据要实现、修改或修复 | 按项目 `AGENTS.md`、现有技术栈、模块和测试实施 |
| 要检查实际变更及测试证据 | `aidev-review-changes` |

`aidev-keep-changes-simple` 作为实际工作的约束，不单独增加阶段；日志整理沿用本流程的参考规则，不为整理单独创建新 Skill。本项目只接入上述五个 Skill，不因当前能力未覆盖某技术就安装整套框架。

## 按改动选择路径

- 小需求、局部调试和 Bug 采用定向修改与相关测试，不重走完整流程。文档是否新建按下文的实现状态判断；仅纠正实现偏差、不改变业务需求时，不新建需求、设计或报告。
- 新功能、复杂业务或设计变化：按下面流程推进。同一项目延续已有文档，不重新初始化。
- 按影响和风险判断大小；权限、公开契约、资金和存量数据变化，即使代码很少也先明确边界及验证。
- 已有授权持续有效，展示计划不等于重新申请批准；只要求设计时不编码。关键业务取舍、超出范围或不可逆操作才核对所需决定。

## 产品沟通与设计

需求不清时用 $aidev-define-product-requirements，页面和用户流程需要设计时用 $aidev-design-interaction。已有清晰规格直接沿用，不重新做一轮产品发现。

明确目标用户、问题、本次范围、关键业务规则、页面行为和可观察验收条件。产品、交互与技术设计在同一上下文中迭代；识别冲突、推断和未解决事项，不编造用户决定。

文档直接放在 `docs/<功能名>/`，文件使用稳定的任务简称：`<任务简称>-需求.md`、`<任务简称>-设计.md`、`<任务简称>-计划.md`。目录不表示开发阶段，完成后不搬动。简称描述业务目标或本次变化，例如“订单退款”“支持部分退款”，不按调试轮次追加 v2 或 latest。

需求按 [需求模板](assets/PRODUCT.md) 描述做什么、规则和验收；开发设计按 [设计模板](assets/DESIGN.md) 说明如何实现。同次任务的文件使用同一简称并通过相对链接互相引用；顶部写创建日期、更新日期和实际状态，变更任务还链接前序需求/设计。日期用 YYYY-MM-DD，未知历史日期注明未知，不编造。按需创建有内容的文件，不预生成整套空档；无需改设计时引用既有设计即可。

按需求是否已有实现决定文档处理，不按文件是否存在或改动行数判断：
- 尚在讨论、设计或本轮开发未完成的内容，持续修改本轮文档；普通调试不另建副本。部分实现时按受影响行为判断，不因整个功能未完成而覆盖已实现部分的业务决定。
- 已实现的历史功能发生业务规则、范围或交互变化，在原功能目录新建本次变更文档，引用前序需求和设计，说明变更前、变更后、原因、影响及新的验收条件。沿用未变部分的定义，不整套复制历史正文，也不覆盖原有决定和验证记录。
- 修复 Bug 以符合原需求，或纠正文档笔误、补充说明，直接修正原文件的相关内容及更新日期；不改历史业务结论。
- 新文档先标明待实现，不能因为日期更晚就取代现行规则。完成并核实相关实现后，在前序文档补充后续变更链接和被替代的具体范围；未变部分继续适用。代码完成、上线生效和人工验收分别说明，不伪造结论。
- 读取当前功能时先读前序定义，再沿已实现变更核对受影响条目；待实现方案单独识别。有冲突先核对实际代码和决定来源，不直接以时间排序裁决。

已有项目沿用合适的文档目录，不为套用新路径自动迁移；跨功能变化选主要归属目录，其他功能引用它。公共规则只定义一处，API Schema 和迁移引用原生文件。

## 开发计划

- 先搜索已有实现、组件、测试和约束，确定所需数据/API/UI、调用方影响及最小方案。新项目按当前需求选择技术栈，复用不等于复制旧项目包袱。
- 按可观察用户行为拆切片，每片写清完成条件、涉及模块和验证方法；避免先堆完全部表、全部接口再做页面。
- 本轮已有计划原地维护；历史功能的新需求需要跟踪时建立本次变更计划，保留旧计划及验证记录。工作需要持续跟踪时，按 [计划模板](assets/PLAN.md) 创建同目录的 `<任务简称>-计划.md`，链接对应需求与设计。开发任务清单、进度和验证放在这份计划中，不另建 TASKS 文档。短任务在回复列计划即可。
- 向用户展示简明计划后，在授权范围内继续。只记录实质范围或方案决定及原因，不逐轮写调试流水账。

## 实现与单元测试

- 按切片接通所需界面、后端和本地数据逻辑，遵循项目规则及现有实现；按实际任务加载已安装的能力，不预设 Java、Vue、数据库或服务端 API。
- 对业务行为变化编写或更新有意义的单元测试，覆盖正常、关键边界、失败和相关回归。可复现 Bug 优先保留失败用例，确认修复后通过；不要为纯文案改动机械加测试，也不要测试实现细节来凑覆盖。
- 使用项目已有构建和测试命令，检查真实退出码；缺工具或服务时如实说明。Mock、单元测试、真实集成和人工验收分别报告。
- 默认不执行浏览器、Playwright/E2E、页面交互或截图验证；仅用户明确要求时执行。代码测试不能证明页面体验。
- 实现后同步受影响文档，正确需求不迁就错误代码。相关代码改变后重验，不能沿用不适用的历史通过结果。

## 反馈记录与复盘

有实质需求、纠正、排障或优化结论时，在 `docs/feedback/YYYY-MM-DD.md` 轻量记录。固定标题 `## [类型] 简短主题`，类型选“需求、纠正、排障、优化、经验”之一，正文三项“背景、处理、结果”，每项一句即可；同一问题连续调试合并记录。有重复问题或用户要求时再按 [协作日志与整理规则](references/feedback-review.md) 汇总，不固定生成周报。日志不代替业务文档，整理先提出优化线索，不自动改通用规范或安装后台任务。

## 交付与继续

在原计划或回复简述改动、实际检查、失败/未验证项，以及人工页面验证的前置条件、操作和预期。本轮文档更新当前真实状态，历史任务的决定和验证记录保留，不生成单独的完成报告。

专项 Review 使用 $aidev-review-changes；不要求每个小改走独立审查。人工反馈继续当前切片，业务规则调整按上述实现状态维护本轮文档或新建变更文档。不得代填人工批准或验收通过；部署和监控不属于默认流程。
