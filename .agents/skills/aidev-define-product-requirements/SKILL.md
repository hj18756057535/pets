# 产品需求沟通

读取用户目标、已有需求和相关约束。未实现或本轮开发中的内容直接更新本轮文档；已实现行为的新需求建立关联前序的变更文档。沿用已有术语和编号，不重新做产品发现。完整开发由 $aidev-manage-development 串起。

- 查明谁在什么场景遇到什么问题、现状如何、希望改变什么。区分来源事实、推断、假设和用户决定；不编造访谈、收益或批准。
- 阅读相关最小资料集，发现冲突时说明来源、影响及待决定的问题。先查资料，只问影响当前范围的关键缺口，可独立完成的工作继续。
- 写清本次做什么、暂不做什么。已有方案沿用；方向未定时比较能解决当前问题的简单方案，不自动扩展成通用产品。
- 按角色、触发/输入、处理规则和输出定义行为。适用时明确权限、状态、字段语义、公式/单位、失败和重复操作；复杂计算给出输入和预期结果。
- 同一规则只定义一处，页面与 API 引用它。沿用已有验收条目和 ID，不为小改建立编号体系。
- 验收条件描述前置、操作和可观察结果，区分代码可验证项和人工页面验证。业务收益与功能完成分开，缺少真实数据时不声称收益达成。
- 需求放在 `docs/<功能名>/<任务简称>-需求.md`，链接对应设计和计划，顶部记录创建/更新日期、实际状态。已实现功能的新需求引用前序文档，说明前后差异和新验收；未变规则直接引用，普通调试不按轮次建新档。处理方式遵循主流程。
- 交互需要展开时使用 $aidev-design-interaction；技术方案按项目规则与现有实现落实。只要求设计时交付设计，已授权开发则继续。

行为确实调整时更新本轮规则和验收；已实现的历史行为通过新变更文档说明，保留前序定义。代码偏离正确需求则修代码。重要取舍保留简短原因与决定来源，普通调试不另建变更报告。
