# 变更审查与验证

读取当前范围、现有需求/设计、项目规则和实际 diff。有计划时查看相关切片；小改不为审查补建任务、规格或报告。遵循 [复用与简化约束](../aidev-keep-changes-simple/SKILL.md)。

负责判断改动是否符合已有需求、证据是否充分，不重新开展产品发现或代替人工验收。审查请求默认只读；已授权修复时调用对应开发能力实施。可由当前 Agent 完成，不强制新增独立 Agent、审查轮次或报告文件。

## 审查重点

- 区分本次变更与用户已有改动，核对受影响路径、调用方和相关未跟踪文件。
- 按需求和验收条件检查业务正确性、授权、数据一致性、边界、失败处理和遗漏测试；兼容、并发和性能只查实际相关风险。
- 检查重复实现、无用抽象、未要求的配置/功能和冗余文档；不给没有实际影响的风格偏好报缺陷。
- 需要时读取相关领域 Skill。每项 Finding 给出严重性、位置、触发条件、影响和证据；疑点没有证据时说明缺口，不当成已证实缺陷。
- 严重性按实际影响判断：阻断泄露/越权/数据丢失或无法交付，高优先级处理核心行为错误，其他可信边界与回归按影响排序。
- 专项审查先报告问题，由主要写入者修复。独立只读审查按规模和当前授权使用，不机械安排固定角色或轮次。

按项目规则与真实实现核对当前技术栈的输入校验、界面调用、后端命令、持久化和数据边界。并发保护只检查本次实际相关问题，不因审查猜测新增锁或引入未安装的领域能力。

## 验证与交接

运行相关单元测试、静态检查或构建，核对真实日志和退出码。修复后重验受影响内容；历史通过不证明当前代码有效。Mock、单元测试、真实集成和人工业务验收分别说明。

文档和代码不一致时先确定正确依据：需求正确则指出代码修复方向，已有修复授权再实施；需求确已调整时按主流程判断修订本轮文档还是建立历史功能的关联变更文档。结果放在原计划或回复，不新建审查报告。默认不运行浏览器或截图验证，提供人工操作与预期，标明未验证项，不代替人工记录通过。
